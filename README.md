### Overview
Configured a private internal LAN "192.168.10.0/24", and a DMZ subnet "192.168.11.0/24" which has multiple hosts like windows 7, kali and metasploitable. 
Established routing, default gateways, and firewall filtering policies to keep watch of internal subnet and outbound internet traffic.

### Key elements of learning
learning least privilege by only permitting:
* ICMP for path diagnostics
* UDP port 53 for external DNS name resolution
* TCP port 443 for encrypted web browsing
* TCP port 80 to expose specific web services between the DMZ and LAN.
Validating service accessibility using network tools such as "telnet ip 80" with raw HTTP request "GET /" and active service enumeration using "nmap ip".

### Key difficulties
The only issues ive had was that first, hosts on the "192.168.11.0/24" subnet didnt have default routes and "8.8.8.8" nameserver entries in "/etc/resolv.conf", resulting in unreachable external hosts.
I fixed this by just checking the resolv.conf file on every linux based device and changing the name server. 

Second issue was that pfsense in "Firewall/Rules/OPT1" had a default rule "IPv4 TCP/UDP - description: DMZ to ubuntu" which was overriding the required "IPv4 ICMP Any" rule, causing the windows 7 to not be able to ping 8.8.8.8 or access google.com. 
I fixed this by just deleting the rule.

### Overview
Conducted reconnaissance, port scanning, and automated service enumeration against the DMZ kali linux and metasploitable machines. Inspected differences between plaintext and encrypted traffic in wireshark, performed HTTP banner identification, and conducted brute force credential attacks against FTP and SMB services.

### Key elements of learning
* Identified cleartext protocols by extracting credentials from telnet in wireshark streams, and encrypted session payloads in SSH.
* Performed HTTP banner grabbing using command "telnet 192.168.10.7 80" to view web server software and operating system versions from response headers.
* Used Hydra for automated credential cracking against the FTP service on port TCP 21.
* Used metasploit auxiliary attack options to enumerate SMB shares, map account SIDs and perform SMB login brute forcing on Windows 7.

### Key difficulties
I ran into 4 issues in this lab.

The first issue was that the metasploitable had trouble booting, but once it did, it booted without an IPv4 address on eth0, making it unpingable. I first noticed this issue when i was attempting to brute force the metasploitable machine, the ftp attack was failing, i restarted the ftp service and eventually checked the IP address. I fixed this by manually running sudo **ifconfig eth0 192.168.11.9 netmask 255.255.255.0 up** and adding the default gateway to pfSense **(sudo route add default gw 192.168.11.254 eth0)**.

The second issue was performing the HTTP banner grab using telnet on the windows 7 machine. The screen remained blank and im not sure why, im sure i ran telnet in lab 1 without issues, and while spamming random buttons to as i first thought it froze... i realised that typing anything but http commands caused the connection to drop with a 400 bad request. But, the grab still succeeded because the error payload itself returned the required Server: **Apache/2.4.52 (Ubuntu)** header.

The third issue was that the kali DMZ booted with an incorrect IP "1.1.1.1" and failed to set a gateway. I resolved this by reassigning 192.168.11.8/24 to eth0, adding the subnet route 192.168.11.0/24 dev eth0, and setting the default gateway via 192.168.11.254.

The last and fourth issue was that hydra dropped connections against ftp with an error that said that all of the children were disabled and was running 16 concurrent tasks which crashed the vsftpd socket. I fixed this by throttling execution with single threading using the command option **"-t 1"**.

## Lab 3: AWS Architecture

### Overview
Deployed and configured both linux ubuntu and windows server 2022 instances within the aws academy learner lab, used us-east-1 region. I also configured security groups and host based firewall (windows defender and aws inbound rules) for services like SSH, RDP, HTTP, ICMP. Deployed Apache and IIS web servers, analyzed access logs, modified instance hardware specifications using the aws cli terminal and implemented cloud automation using python and boto3 scripts.

### Key elements of learning
* Deployed ubuntu server and windows server 2022 ec2 instances, connecting network interfaces with security groups to filter specific services like SSH, RDP, HTTP, and HTTPS.
* Created a second linux administrative user **napier** and updated **/etc/ssh/sshd_config** to enable password SSH authentication as well as the default public key authentication.
* Conducted forensic log auditing by extracting HTTP status codes and user agent headers from Apache **/var/log/apache2/access.log** and windows iis w3c logs in **C:\inetpub\logs\LogFiles\W3SVC1**   verifying the client IP.
* Used the aws cli to execute state changes and resize instance types, such as from t2.micro to t3.small.
* Created python automation scripts with boto3 to enumerate instance states, generate key pairs, create new ec2 instances, and terminate instances.

### Key difficulties
The only issue ive encountered in this lab was an **AuthFailure** error when attempting to run aws cli commands and execute the python scripts from the learner lab terminal.   The lab page under the The aws cli details section instructed to copy and paste the session credentials block directly into **~/.aws/credentials**. But, when I navigated to that directory and attempting to save the file, the terminal gave me a permission denied error. 

To investigate why the file could not be modified, I ran **ls -lsa** to inspect the file and directory permissions and discovered that the file **credentials** was missing write permissions for the user account. I resolved this by manually adding write permissions using the command **chmod ugo+w credentials**. Once the permissions were updated, I pasted the active aws credential details into the file, saved it successfully, and re-ran **aws ec2 describe-instances --region us-east-1**. The command executed cleanly and returned the json payload without any authentication or token errors.
